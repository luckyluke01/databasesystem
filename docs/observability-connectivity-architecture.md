# 可观测系统调用链连通性架构方案

> 本文档汇总针对可观测系统中「观测对象连通性」存储与查询问题的分析与推荐方案。  
> 背景：当前使用 NebulaGraph 存储观测对象之间的连通关系，主要关注连通性而非 Span/Trace 细节。

## 1. 背景与现状问题

### 1.1 业务场景

- **数据本质**：观测对象之间的连通性关系（如服务 A 包含服务实例 1/2，实例之间的调用关系等）
- **数据来源**：从 Trace 中提取观测对象的连通性信息，不重点感知 Span 细节
- **存储方式**：NebulaGraph 图数据库
- **写入模式**：持续推送、复写（Overwrite），写入链路无法精准感知关系是否存在

### 1.2 当前痛点

| 编号 | 问题描述 | 影响 |
|------|----------|------|
| P1 | 关系只能保证相邻节点之间的准确性，跨多跳时关系信息错乱 | 多跳查询结果不可信 |
| P2 | 关系中的 rank 字段未有效使用，历史关系状态感知度低 | 无法回答「过去某时刻关系是否存在」 |
| P3 | 持续复写导致历史被覆盖，写入链路无精准存在性感知 | 只有当前快照，无时序能力 |

## 2. 是否应使用向量数据库

### 2.1 结论

**不建议将调用链连通性数据向量化，并使用向量数据库作为主存储与查询引擎。**

这不是存储选型问题，而是**数据建模问题**。换成向量库会用一个做「近似召回」的工具，去解决一个要求「精确连通」和「精确历史」的问题，方向是反的。

### 2.2 向量数据库 vs 连通性需求

| 连通性需求 | 向量库特性 | 冲突点 |
|------------|------------|--------|
| 精确判断 A 到 B 是否连通 | 近似匹配，返回 top-k 相似项 | 连通性是布尔事实，不是相似度 |
| 多跳可达性（A→B→C→D） | 单跳向量距离，无传递性 | 向量相似 ≠ 图可达，无法做路径/传递闭包 |
| 精确感知一条关系是否存在 | 模糊召回，recall < 100% | 恰恰需要「存在/不存在」的确定性 |

### 2.3 关键认知

> **「A 像 B」和「A 能到达 B」是两件完全不同的事。**

即使使用 node2vec、GNN 等图嵌入方法将拓扑向量化，向量距离表达的是「结构角色相似」，也无法回答「A 经过几跳能不能到达 C」。

## 3. 问题根因诊断

### 3.1 问题 P1：多跳关系错乱

**根因**：将来自不同 Trace 的边拍平合并成一张全局图，丢失了「路径上下文」。

**示例**：

- Trace1 中有 A→B
- Trace2 中有 B→C
- 两者可能并非同一条调用链

一旦拍平进全局图，图查询会「误推」出 A→B→C 这条实际从未发生过的多跳路径。跳数越多，虚假路径的组合爆炸越严重。

**正确做法**：

1. **保留 Trace 维度**  
   多跳可达性应在「同一条 Trace 内」用 Span 的父子（parent_span_id）关系还原真实路径，而不是在拍平后的全局图上做任意 Traversal。

2. **区分边的语义**  
   - **包含关系**：服务 A 包含实例 1/2（相对稳定的层级/归属）
   - **调用关系**：实例→实例（动态、随 Trace 变化）  
   两类边混在同一张图里做 Traversal 是错乱的常见来源，建议分层建模。

3. **跨 Trace 聚合需加约束**  
   若业务需要「统计意义上的可能连通」，应对边做频次/权重约束（如只保留在 N 条 Trace 中共现的边），查询多跳时加路径约束，而非无脑展开。

### 3.2 问题 P2 & P3：历史感知差、存在性无法精准感知

**根因**：持续推送 + 复写（Overwrite）等于不断销毁历史。复写模型下任何时刻只有「当前快照」，自然无法回答「时间 T 时这条关系存不存在/是什么状态」。

**正确做法**：引入**时间维度建模**。

| 改造项 | 说明 |
|--------|------|
| 边的时态化 | 给每条边加 `valid_from` / `valid_to`（或 `last_seen` + TTL），变成时序化/双时态（Bitemporal）模型 |
| 写入模式 | 从「覆盖」改为 **Append-only + 状态推导**：每次观测到关系记录一个带时间戳的观测事件 |
| 存在性推导 | 关系的「存在」= 滑动时间窗内观测计数 > 0；「消失」= 超过窗口无再观测（TTL 或定时物化标记 `valid_to`） |

**写入链路设计**：

1. 写入侧只管「上报观测事件」（`edge_observed @ timestamp`），做幂等去重（按 src+dst+时间窗）
2. **不在写入链路判断「是否第一次出现」**——那是查询/物化侧的职责
3. 原始观测适合用时序数据库 / 宽事件表（列存）承载，再物化出「当前拓扑图」供 NebulaGraph 或直接查询

## 4. 推荐整体架构

### 4.1 架构总览

```
Trace 采集
    ↓
抽取观测对象连通事件（带 trace_id、timestamp）
    ↓
┌─────────────────────────────────────────────────────────┐
│  事件/时序层（Append-only 原始观测）                      │
│  ClickHouse / 时序库 / Kafka + 列存                       │
└─────────────────────────────────────────────────────────┘
    ↓ 定时物化（按时间窗推导边的存在与有效区间）
┌─────────────────────────────────────────────────────────┐
│  图层（NebulaGraph）                                      │
│  边带 valid_from/valid_to/权重，分层（包含 vs 调用）       │
└─────────────────────────────────────────────────────────┘
    ↓
查询层
  - 多跳：Trace 内还原真实路径
  - 跨 Trace：带权重 + 时间约束的受限 Traversal
```

### 4.2 各层职责

| 层级 | 职责 | 存储选型 |
|------|------|----------|
| 事件层 | 原始观测事件、Append-only、幂等写入 | ClickHouse / 时序库 |
| 物化层 | 按时间窗推导边存在性、有效区间 | 定时任务 / Flink |
| 图层 | 当前连通拓扑、浅层实时多跳查询 | NebulaGraph |
| 路径层 | Trace 内完整路径、深层可达查询 | 列存 / 路径表 |

### 4.3 核心原则

- **多跳准确性** → Trace 内路径还原 + 边权重/时间约束，不在拍平图上裸 Traversal
- **历史感知** → 有效区间 / Append-only 事件，不再复写
- **精确存在性** → 时间窗 Liveness 判定 + 幂等写入

## 5. NebulaGraph 深层多跳查询支持

NebulaGraph 提供遍历查询，但**在线深跳数 Traversal 天然不适合作为主查询方式**。深层查询应转为「查预计算结果」或「查物化路径」。

### 5.1 为什么在线深遍历会撑不住

多跳遍历本质是**指数级扇出**：

- 每跳中间结果数 ≈ 上一跳节点数 × 平均出度
- 平均出度 10 时：5 跳 ≈ 10⁵，8 跳 ≈ 10⁸ 量级中间路径
- Nebula 的 `GO` / `MATCH` 逐跳展开 + JOIN，跳数一深则内存爆、延迟飙、甚至 OOM

**正确思路**：不是「怎么让 Nebula 跑得动 8 跳遍历」，而是**把深查询从在线 Traversal 转成查预计算结果或查物化路径**。

### 5.2 方式一：Trace 内路径物化（最推荐）

**思路**：单条 Trace 内的完整路径在采集时就已经是已知的、确定的，无需事后再去图里 Traversal 还原。

**做法**：

- 采集时，用 Span 的 parent 关系还原完整链路（A→B→C→D→…）
- 将路径作为**一等公民「路径对象」**存储，而非只拆成单跳边

**路径表 Schema 示例**：

```sql
-- 方案 A：逐跳存储
CREATE TABLE trace_paths (
    trace_id      String,
    path_id       String,
    hop_seq       UInt8,
    src_obj       String,
    dst_obj       String,
    edge_type     String,
    ts            DateTime64(3)
) ENGINE = MergeTree()
ORDER BY (trace_id, path_id, hop_seq);

-- 方案 B：整路径存储
CREATE TABLE trace_path_objects (
    trace_id      String,
    path_id       String,
    path_nodes    Array(String),  -- [A, B, C, D]
    path_length   UInt8,
    ts            DateTime64(3)
) ENGINE = MergeTree()
ORDER BY (trace_id, ts);
```

**查询能力**：

- 任意深度的「A 是否经过 N 跳到达 D」→ 退化为一次表查询 / 数组包含判断，O(1)~O(log N)
- 多跳准确性问题顺带根治，路径从未被拆散

**Nebula 定位**：只保留「当前聚合拓扑 + 浅层（1~3 跳）实时查询」，深层全部走路径物化表。

### 5.3 方式二：可达性索引（传递闭包预计算）

**适用场景**：只需回答「A 到 B 是否可达」，不关心具体路径。

**做法**：

| 方法 | 说明 | 适用 |
|------|------|------|
| 传递闭包物化 | 离线计算所有可达对 `(src, dst, min_hops, valid_from, valid_to)`，查询时直接点查 | 子图规模可控 |
| 2-hop Labeling | 如 Pruned Landmark Labeling，用 label 求交得可达性/最短跳数 | 大图，空间比全闭包小 |

**可达表 Schema 示例**：

```sql
CREATE TABLE reachability_index (
    src_obj       String,
    dst_obj       String,
    min_hops      UInt8,
    valid_from    DateTime64(3),
    valid_to      DateTime64(3),
    path_count    UInt32  -- 统计窗口内出现次数
) ENGINE = MergeTree()
ORDER BY (src_obj, dst_obj, valid_from);
```

### 5.4 方式三：在线遍历 + 强剪枝

若某些查询必须在线跑，务必加约束把扇出砍掉：

| 剪枝策略 | 说明 |
|----------|------|
| 时间窗剪枝 | 只遍历 `valid_from/valid_to` 命中查询时间段的边 |
| 权重/频次剪枝 | 只走「在 ≥N 条 Trace 中出现过」的边 |
| 类型剪枝 | 包含关系边和调用关系边分开，深遍历只走调用边 |
| 限定 trace_id | 带 Trace 上下文时，遍历限定在单 Trace 子图内 |
| 双向 BFS | 已知起终点时，从两端各走一半，O(d^k) → O(2·d^(k/2)) |

**nGQL 示例（受限变长遍历）**：

```ngql
-- 限步数 + 限时间 + 限边类型
GO 1 TO 5 STEPS FROM "service_A" OVER call_edge
  WHERE call_edge.valid_from <= $ts 
    AND call_edge.valid_to >= $ts
  YIELD dst(edge) AS reachable
| LIMIT 10000;
```

> **注意**：一定要给 `STEPS` 上限和 `LIMIT`，绝不开放无界变长遍历。

### 5.5 方式四：离线图计算

**适用场景**：全图所有可达对、连通分量、最短路径矩阵等重计算。

**做法**：

- 使用 Nebula Analytics / Spark GraphX / GraphScope 跑 BFS、连通分量、传递闭包
- 周期性算完，结果回灌到路径表 / 可达索引
- 在线只查结果，不在线算

### 5.5 方式五：图缩并（降低逻辑跳数）

**思路**：实例级是细粒度大图（跳数多），按「服务」聚合成服务级拓扑图，跳数大幅下降。

**查询策略**：

1. 先在服务级图上做「粗粒度可达性」（跳数浅，Nebula 直接扛）
2. 命中后再下钻到相关实例子图做精确路径

### 5.6 深层查询推荐组合

```
采集 → 还原 Trace 内完整路径
  │
  ├─ 路径物化表（列存）          → 任意深度路径/可达查询（主力，方式一）
  │
  ├─ 离线传递闭包 / 可达索引      → 只问可达性/最短跳数（方式二）
  │
  └─ NebulaGraph（当前拓扑）     → 浅层（≤3 跳）实时查询 + 受限剪枝（方式三）
                                   深层/全量分析交给离线图计算回灌（方式四/五）
```

**一句话总结**：

> Nebula 负责「当前拓扑 + 浅层实时遍历」，深层查询全部转成「查预计算的路径表 / 可达索引」，预计算的源头正是 Trace 本身已知的完整路径。

## 6. 向量数据库的合理定位

向量库**不应作为连通性主存**，但可作为**分析/智能层的补充**：

| 用途 | 说明 |
|------|------|
| 拓扑异常检测 | 用图嵌入（node2vec/GraphSAGE）检测「某实例连接结构突然与历史/同类不一样」 |
| 相似拓扑检索 | 「找出和这次故障调用结构最像的历史片段」 |
| 服务/实例聚类 | 相似拓扑归并、相似故障模式检索 |

这些都是「相似度」问题，适合向量库；但「谁连谁、几跳能到、某时刻存不存在」这类**确定性图问题，继续交给图库 + 时序事件建模**。

## 7. 实施要点总结

### 7.1 不要做的事

- ❌ 用向量数据库替代图数据库存连通性
- ❌ 在拍平的全局图上做无约束深遍历
- ❌ 持续复写覆盖历史关系
- ❌ 在写入链路判断关系「首次出现」

### 7.2 应该做的事

- ✅ 保留 Trace 维度，Trace 内路径还原
- ✅ 边时态化（`valid_from` / `valid_to`）
- ✅ Append-only 事件写入 + 幂等去重
- ✅ 路径物化表承载深层查询
- ✅ Nebula 只做浅层（≤3 跳）实时查询
- ✅ 离线预计算传递闭包 / 可达索引
- ✅ 区分包含关系与调用关系，分层建模

### 7.3 预期收益

| 问题 | 解决方式 | 预期效果 |
|------|----------|----------|
| 多跳关系错乱 | Trace 内路径物化 + 边权重/时间约束 | 多跳查询结果准确 |
| 历史状态感知差 | 边时态化 + Append-only | 可回答任意时刻关系状态 |
| 存在性无法精准感知 | 时间窗 Liveness + 幂等写入 | 精确感知关系存在/消失 |
| 深层查询性能差 | 路径表 / 可达索引预计算 | 任意深度 O(1) 点查 |

## 附录：关键 Schema 参考

### A. 观测事件表（事件层）

```sql
CREATE TABLE edge_observations (
    event_id      UUID,
    src_obj       String,
    dst_obj       String,
    edge_type     Enum('contains', 'calls'),
    trace_id      String,
    observed_at   DateTime64(3),
    -- 幂等键
    dedup_key     String  -- hash(src, dst, edge_type, time_bucket)
) ENGINE = MergeTree()
PARTITION BY toYYYYMMDD(observed_at)
ORDER BY (src_obj, dst_obj, observed_at);
```

### B. NebulaGraph 边属性（图层）

```ngql
CREATE EDGE call_edge (
    valid_from timestamp,
    valid_to   timestamp,
    weight     int,        -- 统计窗口内出现次数
    last_seen  timestamp
);

CREATE EDGE contains_edge (
    valid_from timestamp,
    valid_to   timestamp
);
```

### C. 关系 Liveness 判定逻辑

```sql
-- 关系「存在」= 滑动窗口内有观测
SELECT src_obj, dst_obj, edge_type
FROM edge_observations
WHERE observed_at >= now() - INTERVAL 5 MINUTE
GROUP BY src_obj, dst_obj, edge_type
HAVING count() > 0;

-- 关系「消失」= 超过窗口无观测，物化 valid_to
UPDATE reachability_index
SET valid_to = last_seen + INTERVAL 5 MINUTE
WHERE last_seen < now() - INTERVAL 5 MINUTE
  AND valid_to IS NULL;
```
